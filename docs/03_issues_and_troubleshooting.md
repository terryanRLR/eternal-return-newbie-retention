## A. 데이터 정의 & 정합성 이슈

### 1. 뉴비(신규 유저) 정의가 코발트 프로토콜 유저를 과대 포함시킴
- **증상**: 초기 뉴비 세그먼트 통계가 실제와 다르게 잡힘 — 튜터 피드백에서 "코발트 모드 과대분류 교정"이라는 트러블슈팅을 명시적으로 "백미"로 지목함.
- **재현 조건**: `accountLevel` 등 계정 레벨만으로 뉴비를 정의하고 매칭 모드를 구분하지 않을 경우, 코발트 프로토콜(랭크 모드 성격)의 유저 분포가 일반 스쿼드와 섞여 낮은 레벨 구간의 통계가 왜곡됨.
- **원인 진단**: 코발트 프로토콜은 봇 포함 매칭·별도 랭크 포인트 체계를 가진 모드로, 승률/순위 분포가 일반 스쿼드와 이질적임(실제로 인사이트 문서 1절: "스쿼드 승률 14.0% vs 코발트 50.0%(봇 포함, 평균 1.5위)"). 계정 레벨만으로 필터링하면 이 이질적인 모집단이 섞여 "뉴비"의 성과 지표가 실제보다 부풀려지거나 왜곡됨.
- **해결/결정**: 뉴비를 계정 기준으로 **`accountLevel ≤ 60 AND rankPoint = 0 AND matchingTeamMode = 3(일반 스쿼드)`** 3중 조건으로 재정의. 기획·밸런스 분석 범위 자체도 "일반모드 플레이 유저 로그(코발트 프로토콜은 별도 분리)"로 명시적으로 분리함.
- **근거 자료**: 튜터 피드백(`04_tutor_feedback.md` 1항), 슬라이드 04(데이터 개요 - 분석 범위), 슬라이드 07(뉴비 정의 - 계정 기준 1차 선별), 인사이트 문서 1절(모드 오염 경고).
- **상태**: `해결됨`. 다만 튜터는 "60레벨 컷 근거를 분포·교차표로 박제했어야 함"이라고 추가 지적 — 즉 **컷오프 값(60) 자체의 근거는 슬라이드에 남아있지 않음** (`03-9` 참고, 추가 확인 필요).

### 2. 유저 식별에 닉네임을 쓰면 동일 인물이 중복 집계됨
- **증상**: 닉네임 기준으로 유저를 세면 92,705명이 아니라 93,522명으로 잡혀 유저 수가 부풀려짐.
- **재현 조건**: `groupby("nickname")` 또는 닉네임을 유저 키로 사용하는 모든 집계.
- **원인 진단**: 개명 807건, 동명이인 4건이 존재. 개명한 유저는 닉네임 기준으로 2명으로 카운트되고, 동명이인은 서로 다른 유저가 1명으로 합산됨.
- **해결/결정**: **`userNum`을 유일한 유저 식별 키로 고정**하고, 닉네임은 표시용으로만 사용(예: `nickname=("nickname","first")` 형태로 최초 관측값만 부가정보로 남김 — `notebooks/individual/planner_newbie_kmeans_clustering.ipynb`).
- **근거 자료**: 인사이트 문서 7절 "데이터 품질 처리".
- **상태**: `해결됨`. 잔여 유의사항: `first()`로 뽑은 닉네임은 개명 전 이름일 수 있어 화면 표시용으로만 쓰고 분석 키로는 재사용하지 말 것.

### 3. 수집 기간이 패치 22.1 → 23.0 전환 시점을 걸쳐 있음
- **증상**: 동일 캐릭터·동일 유저의 지표가 기간 내에서 패치로 인해 달라질 수 있는데, 이를 무시하고 기간 전체를 합쳐도 되는지 검증이 필요했음.
- **재현 조건**: 2024-05-30~06-12 전체 기간 데이터를 그대로 groupby하면 패치 22.1(86,874행, 42.5%)과 23.0(117,551행, 57.5%)이 섞임. 패치 경계는 06-05.
- **원인 진단**: (검증 대상 — 실제로는 "문제"가 아니라 "검증이 필요한 가설")
- **해결/결정**: 초보 유저(`accountLevel≤30`, 스쿼드) 기준으로 패치 전후 핵심 지표를 비교 — 초반 사망률(9.7%→9.4%), Top3 진입율(44.7%→43.9%), 평균 킬(2.37→2.33), 피해교환효율(1.01→1.00) 모두 **1%p(또는 0.05) 이내**로 사실상 동일. 캐릭터 사용률 변동도 최대 ±1.6%p(카티야 -1.6%p)로 결론을 바꿀 수준이 아님을 확인 → **합본으로 분석 진행**, 단 `versionMajor`/`versionMinor` 원본 컬럼은 보존해 필요 시 버전별 재분석이 가능하도록 함.
- **근거 자료**: `패치_검증_노트.md` 전문(인사이트 문서에 통합), 슬라이드 없음(부록/발표 멘트로만 존재).
- **상태**: `해결됨`. 대안으로 "23.0만 사용(최신 메타 기준)" 옵션도 검토했으나 채택하지 않음(표본 손실 대비 이득 적음).

### 4. 전체 유저 기준 밸런스 분석과 초보 유저 체감 밸런스가 다름
- **증상**: 전체 유저 기준 승률×픽률 사분면에서는 정상 범위로 보이던 캐릭터(마르티나, 버니스, 셀린, 피올로)가 초보 유저만 따로 보면 이상치 구간에 뚜렷하게 나타남.
- **재현 조건**: 밸런스 사분면 분석을 전체 유저 데이터로만 1회 수행하고 종료할 경우.
- **원인 진단**: 전체 유저는 숙련자 비중이 커서 초보에게만 어려운/쉬운 캐릭터의 신호가 평균에 희석됨.
- **해결/결정**: 동일한 사분면 분석을 **초보 유저 서브셋으로 별도 재실행**, "전체 기준 후보만으로는 부족하므로 초보 구간에서 부각되는 캐릭터를 추가 점검 대상으로 본다"는 원칙을 확정.
- **근거 자료**: 슬라이드 15("전체 밸런스와 초보 체감 밸런스는 다르다").
- **상태**: `완화(정책으로 대응)`. ⚠ **코드 미비**: 이 초보 서브셋 재실행에 해당하는 코드가 `이터널리턴_코드_정리.ipynb`에는 없음. `02_analysis_pipeline.md`의 [3a] 절 cell 11-13 구조를 `accountLevel` 필터를 추가해 재실행한 것으로 추정되나 원본 스크립트 확인 필요.

## B. 분석 방법론 이슈

### 5. 2변량(승률×픽률) 분석만으로는 "왜"를 설명하지 못함 → 다변량으로 확장
- **증상**: 승률×픽률 사분면으로 너프/버프 후보를 골라도, "왜 이 캐릭터가 이상한지"에 대한 설명이 안 됨. 같은 사분면에 있어도 원인이 다를 수 있다는 한계 인식.
- **재현 조건**: 승률·픽률 2개 지표만으로 이상치를 정의하는 모든 분석.
- **원인 진단**: 2개 지표는 상관된 다른 요인(생존시간, 딜, 킬, 등수)을 반영하지 못해 "성능이 이상함"과 "왜 이상한지"를 분리하지 못함.
- **해결/결정**: 승률/픽률/평균등수/평균생존시간/평균딜/평균킬 6개 지표로 **Isolation Forest** 다변량 이상치 탐지를 수행하고(`notebooks/individual/balance_isolation_forest_shap.ipynb`), 탐지된 이상치 각각에 대해 **SHAP**으로 "어떤 지표가 승패를 좌우하는지"를 분해해 원인별로 다른 처방(즉시 너프 / 신중 검토 / 출시 효과 관찰 등)을 내림.
- **근거 자료**: KPT 회고(황현웅, `04_tutor_feedback.md`), 튜터 피드백 2항("절제된 설계가 좋음"), 슬라이드 13-14.
- **상태**: `해결됨`. 튜터가 추가로 지적한 잔여 이슈는 #9 참고(k값/SHAP 산출물이 슬라이드에 충분히 뒷받침되지 않음).

### 6. 이상치 탐지 결과를 그대로 "너프 명단"으로 쓰면 안 됨
- **증상**: Isolation Forest 이상치로 잡힌 8개 캐릭터(나타폰, 다르코, 샬럿, 쇼우, 요한, 마이, 아야, 나딘)를 기계적으로 전부 "너프 검토"로 처리하면 실제로는 성격이 다른 캐릭터를 잘못 처방하게 됨.
- **재현 조건**: `이상치==True` → 자동으로 "너프" 라벨을 붙이는 단순 로직 (`notebooks/individual/balance_isolation_forest_shap.ipynb` cell 12의 `direction()` 함수가 실제로 이렇게 단순 분류함: 승률>평균이면 "너프 검토", 아니면 "성능 개선 검토").
- **원인 진단**: 같은 "이상치"라도 원인이 다름 — 예: 나타폰은 저픽률인데 킬·딜·승률이 동반 상승(직전 버프 효과일 가능성), 다르코는 고픽률인데 승률·등수·생존시간이 낮음(신규 캐릭터라 체험 수요+숙련도 부족 가능성), 샬럿은 딜·킬이 낮아도 승률이 높음(회복/보호 등 비-전투 기여).
- **해결/결정**: 이상치 탐지(Isolation Forest) → SHAP으로 원인 분해 → **캐릭터별 개별 처방**(즉시 너프보다 버프 과보정 여부 점검 / 성능 단정보다 출시 효과 관찰 / 회복·보호 중심 지표로 재검토)이라는 3단계 원칙("이상치 ≠ 즉시 너프")을 최종 결론으로 명문화.
- **근거 자료**: 슬라이드 14("이상치 ≠ 즉시 너프"), 튜터 피드백 2항("같은 이상치도 원인이 달라 처방이 다르다"는 해석이 가장 데이터분석가다운 대목).
- **상태**: `해결됨`.

### 7. 실루엣 점수상 최적 군집 수(k=2)가 실무 활용도와 안 맞음
- **증상**: K-means 군집 수를 2~7까지 실루엣 점수로 비교하면 k=2(0.1915)가 가장 높지만, 이는 "정상군 vs 이상군"의 이분법이라 기획 실무에서 쓰기엔 너무 단순함.
- **재현 조건**: `notebooks/individual/planner_newbie_kmeans_clustering.ipynb` — `for k in range(2,8): ... silhouette_score(...)` 루프 실행 시 k=2가 최댓값으로 나옴.
- **원인 진단**: 통계적 최적값과 서비스 기획에서 필요한 세분화 수준(뉴비/일반/고인물 등 여러 세그먼트)이 항상 일치하지는 않음.
- **해결/결정**: 실루엣 점수 2위인 **k=4를 의도적으로 채택**. 사유를 "기획자 특성상 유저 구분을 뉴비·일반·고인물 등으로 나누어 보는 경우가 더 많다"고 명시.
- **⚠️ 수치 정정 (재실행 확인)**: 이 문서는 원래 `k=4(0.1398)`로 적고 있었으나, 노트북을 다시 실행해 보니 **0.1398은 k=3의 값**이고 **k=4는 0.1448**입니다.

  | k | 실루엣 |
  |---|---|
  | **2** | **0.1915** ← 최고 |
  | 3 | 0.1398 |
  | **4** | **0.1448** ← 2위 (채택) |
  | 5 | 0.1411 |
  | 6 | 0.1181 |
  | 7 | 0.1086 |

  **"k=4가 2위"라는 결론 자체는 맞고, 숫자만 k=3 것으로 잘못 적혀 있었습니다.**
  근거: [`notebooks/individual/02_planner_newbie_kmeans_clustering.ipynb`](../notebooks/individual/02_planner_newbie_kmeans_clustering.ipynb) 실행 출력.
- **근거 자료**: 부록 슬라이드 20.
- **상태**: `완화(정책으로 대응)`. 통계적 근거보다 실무 해석 가능성을 우선한 의도적 트레이드오프이며, 이 판단 자체가 `04_tutor_feedback.md`에서 "구두로만 흘러간" 취약점으로 재지적됨 (#9 참고).

### 8. 몬스터 킬 수가 군집 구분에 과대하게 중요한 것처럼 보임(교란변수)
- **증상**: 군집을 구분하는 피처 중요도(z-score gap)에서 `avg_monsterKill`이 제작·승률보다도 상위에 랭크됨.
- **재현 조건**: `cluster_gap`(피처별 군집간 z-score 격차) 랭킹 상위 확인 시.
- **원인 진단**: 생존시간이 길어질수록 자연히 몬스터를 더 많이 잡게 되므로, `avg_monsterKill`은 독립적인 "실력" 신호가 아니라 **생존시간의 대리(proxy) 변수**에 가까움. 즉 인과가 아니라 상관의 부산물.
- **해결/결정**: 통계적 중요도 수치와 무관하게 **해석 단계에서 `avg_monsterKill`의 중요도를 낮게 판단**하고, 군집 특성 서술에서 비중 있게 다루지 않음.
- **근거 자료**: 부록 슬라이드 21("몬스터킬이 제작·승률보다 중요하다고 나왔지만... 이번 분석에서는 중요도가 낮다고 판단함").
- **상태**: `해결됨(해석 정책으로 대응, 코드/모델 자체는 수정하지 않음)`.

### 9. 전체 승률을 그대로 "적응도" 지표로 쓰면 모드·봇 오염으로 왜곡됨

### 13. characterNum 매핑 누락 여부를 검증하지 않으면 무음 실패(silent failure) 위험

- **재현 조건**: 원본 데이터에 매핑 딕셔너리 범위(1~74) 밖의 `characterNum`이 존재하거나, `characterNum`이 문자열로 들어와 있는 경우.
- **원인 진단**: `.map(lambda x: character_info.get(x, {}).get(...))` 패턴은 실패 시 예외를 던지지 않고 `None`을 반환하므로 누락이 조용히 묻힘.
- **해결/결정**: `characterNum`을 `pd.to_numeric(..., errors="coerce")`로 명시적 형변환 후, 매핑 후 `character_name_kr.isna()`인 행의 `characterNum`을 별도로 뽑아 `print`로 확인하는 검증 스텝을 파이프라인에 고정.
- **근거 자료**: `notebooks/team_final/01_character_mapping.ipynb` cell 3-4 (원본 cell 3-4).
- **상태**: `해결됨`. 74종 전 캐릭터가 매핑 테이블에 존재해 실제 실행 시 unmapped 목록은 비어 있을 것으로 예상되나, 원본 CSV가 없어 최종 확인은 못함.
